# 投稿・通知コンポーネント設計

## 目的

MaterialBlue のタイムライン、返信表示、通知欄で、投稿本文の表示と通知固有の表示を分離する。

目標は、投稿の見た目・挙動を一か所で管理しながら、通知欄では「誰が何をした通知なのか」を投稿本体とは独立して表現できるようにすること。

この文書は設計方針であり、既存コードの一括移動や即時の全面リファクタリングを指示するものではない。実装は既存の Hugo + HTML/CSS + ES Modules + Web Components 構成を維持し、小さな変更単位で進める。

## 基本原則

1. `mb-post` は投稿そのものを表示する。
2. `mb-notification` は通知という出来事・文脈を表示する。
3. 通知対象に投稿がある場合、その投稿表示には `mb-post` を再利用する。
4. 同じ投稿情報を通知専用のHTML/CSSで再実装しない。
5. UIコンポーネントは AT Protocol の取得処理やセッション管理を行わない。
6. データ取得・整形・アクション実行はページ側または既存のアプリケーション層が担当する。
7. CSSは外部スタイルシートで管理し、コンポーネント内に表示用CSSを直書きしない。
8. i18n・日時・数値のフォーマッターなど、アプリケーション依存の機能はホスト側から注入する。
9. 必要のない抽象化や新しいビルド環境・フレームワークを追加しない。

## 責務

### `mb-post`

投稿の共通表示コンポーネント。

担当するもの:

- 投稿者のアバター、表示名、ハンドル
- 投稿本文
- 投稿日時
- 画像・動画・外部リンクなどの埋め込み
- 引用投稿
- 返信スレッドの文脈（取得済みデータとして渡された root / parent）
- リポスト表示など、投稿データに付随する表示情報
- 必要に応じた返信・リポスト・いいね・ブックマーク等のアクションUI

担当しないもの:

- 通知理由（いいね通知、フォロー通知など）の表示
- 通知したユーザーの集約・表示
- 通知一覧の取得、既読化、ページング
- Bluesky API の直接呼び出し
- セッション、Cookie、認証情報の管理
- ページ遷移や通知画面固有の状態管理

### `mb-notification`

通知一覧の1項目を表示するコンポーネント。

担当するもの:

- 通知種別に応じたアイコン・ラベル
- 通知したユーザー、または複数ユーザーのアバター
- 通知種別に応じた説明（いいね、リポスト、返信、メンション、フォロー、引用など）
- 通知時刻
- 未読状態の視覚表現
- 通知種別に応じた対象投稿の表示（いいね・リポストは簡易プレビュー、返信は mb-post）
- 通知項目全体のレイアウト

担当しないもの:

- 返信通知での投稿本体の独自再実装（mb-post に委譲する）
- 通知APIの直接呼び出し
- 既読化APIの直接呼び出し
- 通知データの取得・ページング
- 認証・セッション管理

## コンポーネント構成

```text
Timeline page
  └── mb-post
      ├── author
      ├── reply context (optional)
      ├── post body
      ├── embeds
      └── actions (optional)

Notifications page
  └── mb-notification
      ├── notification header
      │   ├── reason icon
      │   ├── actor avatar(s)
      │   ├── actor name(s)
      │   └── notification time
      ├── notification message
      └── target post (optional)
          ├── like / repost: compact notification preview (no post action buttons)
          └── reply: mb-post
```

`mb-notification` は通知の外枠と文脈を作る。いいね通知・リポスト通知では、画像例のように通知アイコン、アクター、通知文、対象投稿の本文などを簡易プレビューとして表示する。この簡易プレビューには返信・リポスト・いいね等の投稿アクションボタンを表示しない。返信通知では対象の返信投稿を `mb-post` で表示する。対象投稿がない通知（例: フォロー通知）では投稿領域を表示しない。

## データの受け渡し

両コンポーネントは、ホスト側からプロパティとして表示用データを受け取る。DOM属性に複雑なオブジェクトをJSON文字列化して渡すことを標準方式にしない。

概念上の入力:

### `mb-post`

- `post`: AT Protocol の PostView 相当の、描画に必要な情報を含む投稿データ
- `translator`: UI文字列の翻訳関数
- `formatters`: 日時・数値などのフォーマッター
- `actions`: ホストが提供する任意の操作ハンドラー

### `mb-notification`

- `notification`: 通知理由、通知時刻、未読状態などの通知データ
- `actors`: 通知したユーザーの表示情報。複数人をまとめて表示する場合もホスト側で整形する
- `post`: 通知対象の投稿。返信通知では `mb-post` に渡す。いいね・リポスト通知では簡易プレビュー用に使う。存在しない場合は `null`
- `translator`: UI文字列の翻訳関数
- `formatters`: 日時などのフォーマッター
- `actions`: 必要な場合に限り、ホストが提供する操作ハンドラー

上記は設計上の契約案であり、既存のプロパティ名やイベント名を無条件に変更する指示ではない。実装時には現在の `mb-post` のAPIとの互換性を確認し、必要なら段階的に調整する。

## 表示パターン

| 利用場所 | 表示するもの |
|---|---|
| タイムライン | `mb-post` |
| 投稿詳細・返信一覧 | `mb-post` |
| 引用投稿 | `mb-post` の投稿埋め込み表示 |
| いいね通知 | `mb-notification` + アクションボタンなしの簡易投稿プレビュー |
| リポスト通知 | `mb-notification` + アクションボタンなしの簡易投稿プレビュー |
| 返信通知 | `mb-notification` + 対象の `mb-post` |
| メンション通知 | 通知内容に応じた表示。返信投稿として扱う場合は `mb-post` を利用 |
| フォロー通知 | `mb-notification`（対象投稿なし） |

いいね・リポスト通知の簡易プレビューは通知専用UIとして実装し、投稿アクション行を持たせない。返信通知では `mb-post` を利用する。これにより、`mb-post` の投稿UIを通知の種類に関係なく機械的に流用するのではなく、通知の意味に合った密度で表示できる。

## イベントと操作

コンポーネントは操作の意図をホストへ通知し、API呼び出しを自分で行わない。

- `mb-post` は投稿に対する操作イベントを発行するか、ホストから注入されたアクション関数を呼び出す。
- `mb-notification` は通知項目を開く、対象投稿へ移動する等の通知固有イベントをホストへ伝える。
- 既読化は通知一覧・ページ側が管理する。
- イベント名やペイロードは、既存実装との互換性を調査してから確定する。

## CSS・デザイン

- 投稿本体のスタイルは `mb-post` 用の外部CSSに集約する。
- 通知の外枠、通知理由アイコン、アクター表示、未読状態は `mb-notification` 用の外部CSSに集約する。
- 通知内の `mb-post` は、コンテナ幅に応じて自然に縮小できるようにする。
- 画面幅ではなくコンポーネントの利用可能幅に依存する調整には Container Queries を検討する。
- Material Design 3 の既存トークンとタイポグラフィを利用する。
- 表示目的の `style` 属性や、JavaScriptによるCSS文字列の注入を新たに増やさない。
- 長い表示名・ハンドル・本文・URL、画像を含む投稿で横方向のはみ出しを発生させない。

## 実装順序

1. 現在の `mb-post` のプロパティ、イベント、CSS、読み込み方法を棚卸しする。
2. `mb-post` の投稿表示とアプリケーション依存を分離する。既存の動作を維持しながら段階的に行う。
3. タイムラインで `mb-post` を共通利用し、表示差異を確認する。
4. `mb-notification` を通知固有の外枠として実装する。
5. 通知対象投稿を `mb-post` に渡し、投稿表示が重複実装されていないことを確認する。
6. いいね・リポスト・返信・フォローなど通知種別ごとに表示を検証する。
7. デスクトップとモバイル、長いテキスト、画像、未読状態、投稿が存在しない通知を検証する。

各段階は目的別のブランチまたはPRに分ける。設計文書の追加だけで、既存コードの一括移動や全面書き換えを行わない。

## 完了条件

- タイムラインと通知欄で投稿本文・投稿者・埋め込みの基本表示が共通コンポーネントから生成される。
- 通知固有のアイコン・アクター・通知文・未読状態は `mb-notification` が担当する。
- `mb-post` が通知APIや通知理由に依存しない。
- 返信通知の投稿描画は `mb-post` を利用する。
- いいね・リポスト通知はアクションボタンのない簡易プレビューを使い、通常の `mb-post` アクション行を表示しない。
- API通信・認証・既読化はホスト側に残る。
- CSSが外部ファイルで管理され、既存のMaterial Design 3・レスポンシブ方針と整合する。
- 既存の投稿・通知機能を壊さず、Hugoのビルドと対象画面の動作を確認できる。
